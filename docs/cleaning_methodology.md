## 1. Core Engineering Philosophy

The data ingestion pipeline built in Milestone 3 strictly adheres to the principle of **non-destructive, auditable data engineering**:
1. **Raw Immutability:** Raw input datasets in `NEW/data/raw/` are immutable authoritative source files and are **never modified, overwritten, or truncated in place**.
2. **Zero Row Deletion:** Every single raw observation (1,569,168 India rows + 218,791 Maharashtra rows = 1,787,959 total records) is retained in the processed outputs. No rows are discarded.
3. **Explicit Quality Flagging:** Quality anomalies are tagged via explicit, auditable metadata flags rather than silent heuristic filtering.
4. **Preservation of Raw Values:** Measurements, coordinates, and textual fields are preserved verbatim in raw columns (`water_level_raw`, `source_lat`, `source_lng`, `state_raw`, `status_raw`, `trend_raw`) alongside normalized fields.
5. **Separation of Observation Paradigms:** High-frequency continuous telemetry (Maharashtra) and periodic seasonal surveys (India) are processed and stored in dedicated output paths to prevent invalid numerical conflation.

## 2. Ingestion Pipeline Architecture

The ingestion pipeline is implemented as a clean, modular Python package under `NEW/src/data/`:

```text
NEW/src/data/
├── __init__.py           # Package exports
├── loaders.py            # File discovery, schema validation, and provenance attachment
├── normalization.py      # Column cleanup, deterministic coordinate swapping, timestamp parsing
├── quality.py            # Transparent, configuration-driven quality assessment and flag assignment
└── pipeline.py           # Pipeline orchestration, parquet writing, and metric reporting
```

## 3. Transformations & Automatic Corrections

Only **one** automatic geometric correction is performed by the pipeline, strictly guided by forensic evidence:

### A. Deterministic Coordinate Inversion Correction (`output1final.csv`)
- **Forensic Evidence:** In `output1final.csv` (January observations), the column labeled `'lat'` contains Longitude values ($68.5^{\circ}\text{E} - 96.2^{\circ}\text{E}$) and `'lng'` contains Latitude values ($8.1^{\circ}\text{N} - 34.6^{\circ}\text{N}$).
- **Transformation Applied:**
  - `source_lat` and `source_lng` preserve the raw CSV values verbatim.
  - If `source_file == 'output1final.csv'`:
    $$\text{latitude} = \text{source\_lng}$$
    $$\text{longitude} = \text{source\_lat}$$
    $$\text{coordinate\_inverted\_corrected} = \text{True}$$
  - For all other source files, $\text{latitude} = \text{source\_lat}$ and $\text{longitude} = \text{source\_lng}$.
- **Quality Flag Assigned:** `COORDINATE_INVERTED_CORRECTED` (applied to all 389,154 rows).
- **Scope Restriction:** Coordinate inversion is **never applied globally** to any other source files.

### B. Column Whitespace Normalization
- Column names are stripped of whitespace and lowercased (`'BLOCK '` $\rightarrow$ `'block'`, `'VILLAGE '` $\rightarrow$ `'village'`).
- Phantom export columns generated by trailing CSV commas (`Unnamed: 4`, `Unnamed: 7`, `Unnamed: 13`, `Unnamed: 14`, `Unnamed: 15`) are removed **only in the normalized output DataFrame**, leaving raw files untouched.

### C. Timestamp Normalization
- India dates (`%d/%m/%Y`) are parsed into ISO 8601 date strings (`YYYY-MM-DD`), with `observation_year` and `observation_month` extracted. Raw dates are preserved in `date_raw`.
- Maharashtra telemetry timestamps (`%d-%m-%Y %H:%M`) are parsed into ISO 8601 strings (`YYYY-MM-DDTHH:MM:SS`). Raw timestamps are preserved in `data_acquisition_time_raw`.

## 4. Quality Flag Catalogue & Definitions

### A. Empirical Screening Thresholds (`DATA_QUALITY_SCREENING_THRESHOLD`)
The 150m, 500m, and telemetry bounds are explicitly defined as empirical **`DATA_QUALITY_SCREENING_THRESHOLD`** screening rules to identify records requiring human or domain review, **not** scientifically validated immutable groundwater physical limits. Observations exceeding these thresholds are never deleted or claimed to be definitively physically impossible; they are preserved in the processed datasets and excluded from analytics solely via the explicit quality flag (`is_analytics_ready = FALSE`).

### B. Quality Flags Catalogue
Quality flags are stored as semicolon-delimited string arrays in the `quality_flags` column:

| :--- | :--- | :--- | :--- | :--- |

## 5. Water Level Measurement Semantics & Units

To maintain strict scientific integrity, the pipeline explicitly distinguishes among four distinct data dimensions:
1. **Observed Raw Value (`water_level_raw`):** Unaltered numerical value preserved verbatim as recorded in source data. No numerical conversion or scaling is performed.
2. **Known Unit (`water_level_unit`):**
   - **India Dataset:** Set to `UNKNOWN`. Authoritative source metadata does not explicitly specify the measurement unit in column headers (`waterLevel`); the pipeline does not claim "meter" merely from numerical appearance.
   - **Maharashtra Dataset:** Set to `'meter'`. Directly verified from authoritative source column header: `Groundwater Level Telemetry 6 Hourly (meter)`.
3. **Inferred / Possible Interpretation:**
   - In India periodic seasonal datasets, numerical ranges ($0$ to $40+$) are commonly interpreted in groundwater literature as depth below ground level (m bgl) under CGWB conventions, but this interpretation is documented as an unverified working hypothesis, not presented as established fact.
4. **Unresolved Reference Datum (`water_level_reference` / `reference_datum`):**
   - Set to `UNKNOWN` for both India and Maharashtra. For Maharashtra telemetry, the physical reference datum (e.g. sensor depth, casing collar, or mean sea level offset) remains unconfirmed pending GSDA technical documentation.

## 6. Status and Trend Provenance (`LABEL_PROVENANCE_UNVERIFIED`)

Statistical analysis in Milestone 2 revealed that `status` and `trend` in the India periodic dataset exhibit uniform, non-physical distributions uncorrelated with water level changes. However, absent authoritative CGWB provenance documentation, these labels are **not** definitively declared synthetic. 

Instead:
- The fields are stored verbatim as `status_raw` and `trend_raw`.
- Every record possessing these fields is tagged with `LABEL_PROVENANCE_UNVERIFIED`.
- Both fields are **strictly quarantined and excluded** from:
  - Machine learning targets
  - Machine learning feature matrices
  - Early-warning alert labels
  - Ground truth evaluation

## 7. Analytics Readiness Certification (`is_analytics_ready`)

The pipeline introduces the boolean column `is_analytics_ready`:
- **`is_analytics_ready = TRUE`:** Observation passes all empirical screening bounds, has valid geographic coordinates, and contains no unresolved duplicates.
- **`is_analytics_ready = FALSE`:** Observation possesses at least one critical disqualifying flag (`COORDINATE_MISSING`, `COORDINATE_OUT_OF_BOUNDS`, `EXTREME_WATER_LEVEL_REVIEW_REQUIRED`, `SEVERE_EXTREME_WATER_LEVEL_REVIEW_REQUIRED`, `EXACT_DUPLICATE`, or `CONFLICTING_DUPLICATE`).

## 8. What Remains Unresolved & Limitations

1. **Physical Reference Datum of Maharashtra DWLR Telemetry:**
   While the pipeline preserves `water_level_raw` and explicitly assigns `water_level_reference: 'UNKNOWN'` and `reference_datum: 'UNKNOWN'`, official GSDA engineering manuals are needed to mathematically define casing collar elevation offsets.
2. **Missing Measurement Unit in National Seasonal Data:**
   `water_level_unit` remains `UNKNOWN` until authoritative CGWB data dictionary documentation confirms whether levels are meters below ground level (m bgl).
3. **Missing Station Identifiers in National Data:**
   The India dataset relies on `candidate_site_id` generated from administrative names and 4-decimal-place coordinates (~41,069 unique candidate sites). Small GPS variations (e.g. 5th decimal place) over 30 years could split a single well. Formal spatial clustering will be evaluated in subsequent milestones.
4. **Concatenated Administrative Strings:**
   The 1,318 rows with concatenated Dadra & Nagar Haveli strings are preserved with `MALFORMED_ADMIN_GEOGRAPHY`. Because their coordinates and water levels are physically valid, they remain analytics-ready for spatial queries, but require administrative cleaning before district-level grouping.
